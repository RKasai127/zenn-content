## そもそもサーバ証明書とは

サーバ証明書とはクライアント/サーバが挨拶(これから接続しに行きますよの声掛け)を行った後にサーバ側から送られてくる名刺のようなものです。

名刺なので誰かから認証を受ける必要があります。現実では会社が発行してくれますが、インターネットの世界では認証局が発行しています。

管理については現実と同様に発行者(サイト運営者)が管理します。

詳しくは以下のページが分かりやすいので見てみてください。

https://wa3.i-3-i.info/word111698.html

## 証明書の構造について

証明書はASN.1と呼ばれるデータ構造で定義されたデータをBER(DER推奨)エンコードしたものです。
この規格をだれが決めているのかというと、IETF（Internet Engineering Task Force)です。

IETFは簡単にいうとインターネット関連のルールを決めている組織で、そこで決まった技術仕様はRFCと呼ばれます。

RFC5280ではサーバ証明書そのもの(TLS通信で実際に流れる中身)を、
RFC7468でサーバ証明書をテキスト化(.pemや.crt)した時の構造が定義されています。

https://datatracker.ietf.org/doc/html/rfc5280#section-4.1

> The X.509 v3 certificate basic syntax is as follows.  For signature
> calculation, the data that is to be signed is encoded using the ASN.1
> distinguished encoding rules (DER) [X.690].  ASN.1 DER encoding is a
> tag, length, value encoding system for each element.

rfc5280の4章1節には、セクション冒頭で示した、

- ASN.1構造のデータであること
- DERエンコードすること

が記載されています。

また、rfc7468の2章に証明書(テキスト化したもの)の全体ルール・3章に厳密な定義が示されています。以下のようなことが書かれています。

https://datatracker.ietf.org/doc/html/rfc7468

> Textual encoding begins with a line comprising "-----BEGIN ", a
> label, and "-----", and ends with a line comprising "-----END ", a
> label, and "-----".  Between these lines, or "encapsulation
> boundaries", are base64-encoded data according to Section 4 of
> [RFC4648].  (PEM [RFC1421] referred to this data as the "encapsulated text portion".)

- -----BEGINラベルで構成される行ではじまること
- -----ENDラベルで構成される行で終わること
- BEGIN・ENDの間の要素を`encapsulation boundaries`と呼ぶ

## 中身を見てみる

証明書(テキストベース)の中身がデータをDERエンコードしたものをさらに、Base64エンコードされた文字列であることが分かったので、さっそく中身を見ていきましょう。

opensslコマンドに証明書を扱う時ように、便利なサブコマンドが用意されていますのでそちらを使います。

```bash:bash
openssl x509 -in 証明書ファイル -noout -text
```

以下コマンドの説明です。

| コマンド | 意味 |
| --- | --- |
| openssl | opensslコマンド本体 |
| x509 |x509証明書を扱う時に利用するサブコマンド |
| -in 証明書ファイル |入力ファイル |
| -noout | 証明書そのものを出力しない |
| -text | 中身を全て項目名付きのテキストで表示する(-pubkeyなど項目名単位でも指定可能) |

処理冒頭で示した証明書で実行すると以下のようになります。
